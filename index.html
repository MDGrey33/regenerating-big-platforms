1

Don't Rewrite — Build A Foundry

The pointYou don't rewrite the heavy platform; you build a foundry that converts it into clean, regenerated slices one at a time.

In depth

The greenfield thesis — code is disposable, so protect the spec, contracts, tests and schema — works only because regeneration is both cheap and safe. A heavy platform breaks the "safe" half: there is no written spec, the tests don't exist or can't be trusted, the database is shared, and the blast radius of any change is the whole business. The big-bang rewrite is the classic graveyard.

So invert the move. Don't try to regenerate the platform — stand up a repeatable foundry (a pipeline plus a platform team) that lifts one bounded capability out of the legacy, gives it the durable layer it never had, regenerates it safely behind a stable boundary, and moves on.

The 50× arrives slice by slice, not all at once — and a large fraction of the platform may never go through the foundry at all. That isn't failure; it's the correct end state (see card 12).

2

Why the 50× Won't Transfer

The pointEvery precondition that makes regeneration cheap is missing on a brownfield, so you must manufacture them before any 50× is possible.

In depth

Cheap regeneration rests on four things being present. On greenfield you author them as you go; on a brownfield they're absent, which is exactly why the multiple doesn't transfer for free.

  • Spec — greenfield: written intent. Brownfield: intent lives in people's heads and in the code's accidents.
  • Tests — greenfield: a harness you trust. Brownfield: weak, coupled to the implementation, or absent.
  • Schema — greenfield: clean and owned. Brownfield: one shared database many systems couple to directly.
  • Blast radius — greenfield: small and isolated. Brownfield: enormous — everything touches everything.

The work of cards 5–10 is literally manufacturing these four (plus performance) for one slice at a time. Until they exist for a slice, that slice cannot be safely regenerated — full stop.

3

The Unit: One Mediated-Seam Slice

The pointThe unit of work is one capability behind a single instrumentable seam, whose writes are wrapped in a transaction and routed through a mediation layer that owns the contested data.

In depth

You never regenerate "the system" or even "a service." The atomic unit is a mediated-seam behavioural slice — the smallest thing that can carry its own durable layer and be swapped safely:

  • One instrumentable call seam — a single boundary you can route, shadow, and roll back at.
  • Transaction-contained writes — the slice begins and commits its own transaction; it is not entangled in a transaction other code controls.
  • Routed through a write-mediation layer that owns the contested rows. Ownership is a property of the mediator, not the slice — claiming a slice exclusively owns rows in a shared schema is a category error.
  • A closed contract perimeter — ideally ≤5 external consumers, enumerated from DB grants and change-data, not from a trace window.

Classify each slice up front as stateless (an atomic flag-flip rolls it back) or stateful (owns caches, sessions, leaders → needs a drain / pre-warm / overlap cutover, never an instant flip).

4

What is NOT a regeneration unit

The pointToo small can't carry the durable spec and tests, too big drags its coupling along, and data is never regenerated — only evolved.

In depth

Picking the wrong granularity is the most common early mistake — and it quietly dooms the effort.

  • A file — too small to carry a spec, contracts, and a test oracle.
  • A microservice / repo / module — drags all of its coupling along; you inherit the tangle you were trying to escape.
  • A user story — too small to amortise the cost of manufacturing the durable layer.
  • The database schema — data is never regenerated. It only evolves, additively, via expand/contract (card 7).
  • An entangled-transaction slice — any capability whose writes live inside a multi-writer transaction it doesn't control is ineligible until that transaction is decomposed (saga/outbox), funded as its own project.

Right-sizing is the whole game: big enough to carry the quad, small enough to verify and roll back.

5

The Spine: Regeneration Starts at Stage 4

The pointRegeneration doesn't begin until the 4th of 7 stages — everything before it is plumbing and proof, and decoupling the data (S-1) is the long pole.

In depth

Seven stages — and the order is the discipline. The instinct is to jump straight to S3 (let the agent write code); resist it.

  • S‑1 · Write mediation / decouple data — the real long pole. Route every writer of contested rows through one mediation layer; contain transactions. Produces zero regenerated code and can take quarters. Tell leadership this up front.
  • S0 · Cartography & selection — map from the DB change stream (not app traces); pick slice #1 by economics first, safety-feasibility second.
  • S1 · Manufacture the durable layer + PROVE the oracle is complete (card 9). Still no regeneration.
  • S2 · Insert the seam — a behavioural and performance no-op, routing defaulted to legacy.
  • — THE GATE — plumbing done, oracle proven; only now may code be regenerated.
  • S3 · Regenerate + differential-test offline — the first regeneration, stage 4 of 7.
  • S4 · Shadow live → canary cutover (card 11).
  • S5 · Delete legacy, contract the schema, institutionalise.

If you remember one thing: regeneration is the last third of the work, not the first.

6

Manufacture ownership before you regenerate

The pointOn a shared database nothing owns the data, so you route every writer through one mediation layer to manufacture ownership before a slice can be safely regenerated.

In depth

The shared database — not the code — is the boss fight. On a big-ball-of-mud schema many services read and write the same rows directly, so nothing owns anything and you can't safely change a slice's data behaviour.

The fix is to manufacture ownership without physically splitting the database:

  • Stand up change-data-capture (WAL/CDC) to find the true transitive write-set — triggers, stored procs, FK cascades, materialised views — all invisible to app-level tracing.
  • Census every co-writer and co-reader from DB grants + the data dictionary + a credential audit.
  • Route all of them through a single write-mediation service — the only door to those rows.
  • Each slice then reads and writes only through owned views / repositories.

Only mediated, transaction-contained columns are eligible to host a regenerated slice.

7

Expand–Contract: Schema Change Without Breaking

The pointNever break the data: add the new schema additively, run old and new in parallel, prove zero drift, and only then remove the old.

In depth

You change the schema additively and reversibly — never destructively:

  • Expand — add the new column/table alongside the old. Nothing breaks; existing readers keep working.
  • Migrate — dual-write to old and new; backfill historical rows.
  • Shadow-verify — reconcile old vs new continuously via CDC; require zero drift.
  • Contract — drop the old only after a DB-level read-tripwire proves zero readers across the longest external cadence (quarterly regulatory extracts, not last week).

This is why a rollback should never require a data migration — if it does, expand/contract was violated. Co-writer migration is a fleet-wide dependency scheduled before a slice's cutover, not a per-slice afterthought.

8

The Oracle Replaces Lost Determinism

The pointThe LLM that wrote the code isn't deterministic, so a deterministic 4-layer oracle — not a human eyeballing diffs — decides whether each regeneration is correct.

In depth

An LLM regeneration is non-deterministic — so a deterministic oracle, not a human reading a diff, decides whether a regen is correct. Four layers:

  • Characterisation / golden-master — captured production I/O over the longest business cycle the slice touches (year-end, month-end), plus synthesised rare-event rows.
  • Property + metamorphic invariants — implementation-independent rules that survive a full rewrite (example-based unit tests don't).
  • The legacy-mutation completeness gate — card 9; the only non-circular proof the oracle actually has teeth.
  • (Regulated only) an independent compliance oracle that can fail a behaviour the equivalence oracle passes.

Precedence: the corpus (what it "does") beats an authored invariant (what it "should") by default; conflicts are promoted to a named "suspected load-bearing bug" for human adjudication — never silently muted. Equivalence defaults to exact; every downgraded field is a signed, reviewed canonicalisation.

9

Matching legacy proves consistency, not correctness

The pointMatching the old system only proves you copied it — to prove your tests can actually catch bugs, deliberately break the legacy and require your harness to turn red.

In depth

The seductive trap: your regen produces the same output as the legacy, the tests are green, ship it. But "green against the incumbent" only proves consistency, not completeness. If the legacy has a bug, the regen copies it and the tests stay green — blind to it. On its own this is a false-confidence machine that launders unknown bugs into freshly-attested production code.

The fix is mutation testing against the legacy: deliberately inject behaviour-changing mutants into the incumbent and require your harness to turn red. If it stays green, your tests can't see that behaviour — every surviving mutant is a measured blind spot that must be reviewed before the slice is eligible.

This is the single most-skipped and most-important step in the whole model.

10

Manufacturing The Durable Layer

The pointYou can't protect a durable layer that doesn't exist — on a brownfield you manufacture it by harvesting it backward out of the running system.

In depth

On greenfield you author the durable layer forward; on a brownfield you harvest it backward from the running system. Five artifacts:

  • Spec — harvested: AI drafts capability hypotheses from code + CDC + traffic; the domain owner corrects the draft (people correct better than they author from blank) and signs the edge-case exceptions. Regulated slices are the exception — their spec is authored forward from the regulation, and legacy divergence is a finding to adjudicate; the legacy may be the thing that's wrong.
  • Contracts — versioned IDL/OpenAPI + consumer-driven (Pact) contracts, built from DB grants + CDC, never app-edge tracing.
  • Tests — the four-layer oracle (card 8).
  • Schema — owned views + expand/contract (card 7).
  • Performance — the 5th artifact: capture p50/p99/p99.9, throughput, query plan, lock-hold and pool footprint, and gate it offline in CI, co-equal with correctness. A functionally-perfect, 3× slower slice must fail.
11

How a regeneration earns live traffic

The pointA regeneration wins live traffic one reversible step at a time, with the old system kept fully warm so rollback is instant.

In depth

A regen earns production gradually and reversibly — it never just "goes live":

  • Fail-closed seam — any input the harness never characterised routes to legacy or errors loudly; an unverified path never guesses.
  • Offline diff — zero unexplained functional diffs against the oracle, plus the performance gate, before any live capacity is spent.
  • Isolated shadow — replay 5–10% of live traffic on isolated infra (read-replica, separate pool/cache), capped globally, with an SLO-burn kill-switch. Shadow is a guest, never a co-equal tenant.
  • Cascade test on a production clone — for write slices, prove the full side-effect cascade (real triggers/procs/CDC fire), not just the values the slice wrote.
  • Canary 1→5→25→50→100% with machine-driven auto-rollback (no human in the retreat path); stateful slices use pre-warm / drain / overlap, not a sub-30-second flip.

The incumbent stays fully warm the entire bake; one auto-rollback freezes the slice and pages a human (anti-flap), rather than re-canarying into the same failure.

12

Regenerate Only When ROI Clears

The pointRegenerate only the few slices where multi-year savings beat the durable-layer plus verification cost — for most of the platform, "never regenerate" is the correct, permanent answer.

In depth

Regeneration is not free — the cost moves from writing to manufacturing-and-verifying the durable layer. So gate every slice on honest economics:

regenerate only if  (regen frequency over 2–3 yrs × saving vs AI-assisted hand-maintenance)  >  (durable-layer opex + N × verify cost)

Two traps: measure against an AI-assisted hand-maintenance baseline (not unaided manual work — that inflates the win), and keep two ledgers — amortising foundry CAPEX vs non-amortising per-slice OPEX, with break-even computed against the opex.

Five categories are always hand-maintained:

  • Low-churn stable — won't change enough to repay the quad.
  • Data-entangled — can't be decoupled yet.
  • Cannot-certify — intent unrecoverable; the oracle fails the mutation gate.
  • Regulated where re-certification > change value — the honest multiple here is ~2–5×, not 50×.
  • No DB headroom — the safety machinery itself would breach the SLO.

"Slices correctly never regenerated" is a success metric, not a backlog.

13

Stop Reviewing Code, Own The Spec

The pointHumans stop guarding code diffs and start authoring the spec, contracts, and oracle — and the platform team paves the road instead of approving every regeneration.

In depth

The hardest change is cultural, not technical. The whole point is that humans stop reviewing generated diffs (there are too many, and the diff isn't the durable artifact) and instead author and own the spec, contracts, and oracle — the harness verifies automatically, and humans adjudicate only the residue the oracle can't decide.

Team shape (Team Topologies):

  • A Regeneration Platform team owns the paved road — the seam, mediation layer, oracle/harness, comparator, perf-gate, provenance ledger, global invariant monitors. It audits the eligibility gate but is never a per-regen approver, or it becomes the bottleneck everyone routes around.
  • Stream-aligned custody teams own the durable layer of their own slices.
  • An independent validation function (model-risk / SR 11‑7 style) challenges regulated regens — the builder can't be the sole certifier.

Fund the durable layer as compounding platform investment, never a time-boxed project — a time-boxed harness rots and the org silently reverts to protecting code. Reward owning the spec and correctly not regenerating — not code heroics.

14

Track these, not those

The pointMeasure whether behavior is truly covered and the platform stays fast — not lines of code or raw delivery speed.

In depth

Measure the things that actually de-risk regeneration; the classic dashboards mislead here.

Track:

  • Behavior-coverage (held-out production traffic replayed within tolerance) reported with the mutation kill-rate — never a single coverage % against an invented denominator.
  • Platform headroom + end-to-end p99 of the top-10 hottest paths — these govern cadence; capacity gates how fast you can fan out.
  • Human-hours-per-regen as a falling curve (flat = a verification bottleneck forming = an incident); structurally flat on regulated slices by design.
  • Escaped-divergence after cutover → 0 (the headline safety metric).
  • Rollbacks needing a data migration → 0 (non-zero means expand/contract was violated).
  • Slices correctly never regenerated — counted as wins.

Ignore: line coverage (theatre on legacy), velocity / story points, and lines-of-code regenerated — speed of writing is exactly the thing that just became cheap, and therefore meaningless.

15

The One Risk That Sinks It

The pointThe fatal failure is confidently reproducing behavior nobody understands on a crown-jewel slice — so build the machine to make that case loud and gated, never silent.

In depth

The harness is manufactured from the same un-understood system it has to certify — so its completeness, not its consistency, is the load-bearing unknown. And the danger correlates exactly the wrong way: the slices where the corpus is structurally thinnest (high-coupling, irregular-cycle crown jewels — month-end close, settlement, eligibility) are precisely where the stakes and the hidden couplings are highest.

The mutation gate, coupling discovery, fail-closed seam, global invariant monitors, and the CANNOT-CERTIFY verdict measure and bound this risk — they cannot eliminate it.

The single fatal failure mode is shipping a confident, provenance-stamped, behaviourally-equivalent reproduction of behaviour nobody actually understands. Design the machine so that outcome is loud and gated — never silent and attested. When in doubt on a crown-jewel slice, the right answer is hand-maintain (card 12).
